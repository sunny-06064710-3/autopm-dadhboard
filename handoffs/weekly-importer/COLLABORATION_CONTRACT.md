# AutoPM 协作保护契约

版本：1.0（公开脱敏版）　建立日期：2026-09-23

使用入口：[详细说明和限制](docs/IMPORTER_USER_GUIDE.md)；本次仅发布文档，适用本机 rc5，不代表本目录历史源码已升级。

## 生效范围与真实保护能力

本契约约束周报导入工具的后续协作，依据用户要求：必须事先解释限制，已经确认的规则不得擅自修改。

**已落实：项目协作规则和保护清单。未落实：独立于执行者的权限门禁、受保护分支及完整的契约测试。** 本文不是文件不可修改、Airtable 不可修改或其他 AI 自动遵守的技术证明。新工作区须携带本契约；其他工具须明确加载它。

## 1. 保护对象是什么

保护对象是「业务含义 + 稳定标识 + 数据关系 + 修改权限 + 验收证据」。不能只锁中文/英文显示名称，也不能把程序当前的错误假设永久冻结。

每项保护记录应包含：规则编号、业务含义、适用 Base/表/字段 ID、允许的修改、禁止的修改、上下游影响、检查方法、解除保护的批准记录。

不在清单中的对象是“未核对”，不等于可以随意修改。先检查它是否参与现有数据关系或写入流程，再作判断。

## 2. 三种改动级别

| 级别 | 典型对象 | 执行规则 |
|---|---|---|
| 可以正常修改 | 工程进展正文、明确的新日期、界面间距和配色 | 在已授权任务内执行；涉及新预览内容时使旧预览失效 |
| 可以修改，但需兼容检查 | 工厂显示名称/代码、字段显示名称、周报表头和布局、SKU 清单 | 先列依赖并验证匹配与解析；不能偷偷假定这些值永远不变；发现不兼容须说明影响，保留原数据并阻止受影响写入 |
| 已保护，未经专项批准不得修改 | 已确认业务规则、记录身份与关联含义、写入权限边界、删除/合并规则、校验与验证要求 | 广义“修复、优化、最高等级、全部处理”不自动解除保护。必须拿出具体改前/改后与迁移预览，再取得用户对该项变更的明确批准 |

“可以正常修改”不授予代理任意写入生产数据的权限；具体执行范围仍以用户当前授权为准。

## 3. 已生效的保护规则

| ID | 保护规则 | 可以做 | 不得擅自做 |
|---|---|---|---|
| P01 | 身份不能靠名称碰巧相同来继承 | 保持表、字段、记录 ID 并适配显示名称变化 | 删除重建后按同名静默接管；合并同名工厂；把任务挂到猜测的项目 |
| P02 | 工厂代码属于可变业务值 | 支持 FAC 改号，依据明确名称映射和实际关联匹配 | 重新要求用户恢复旧代码；将不明后缀全部裁掉；把不同真实工厂当成别名 |
| P03 | 完成任务使用 Task Done (Manual) checkbox | 对有源证据的完成任务勾选 True | 写入公式状态字段；推断 Completed By；仅因周报没有绿色而把已完成改回 False |
| P04 | 来源不明确不能伪装成确定数据 | 展示源单元格、原因、受影响项目/任务与处理方法 | 猜日期、猜型号、把来源未解析称为无变化，或把未比较称为没有任务 |
| P05 | 预览与实际写入分开 | 对本次已确认预览执行对应写入 | 无新证据扩大到其他项目、整个库、删除或合并；把模拟成功当作生产成功 |
| P06 | 写入安全检查必须保留 | 修复实现、加强检查，允许明确无关项目独立处理 | 关闭结构检查、身份核对、源文件变更检查、写前冲突检查、写后验证以获得“成功” |
| P07 | 重复导入不能制造重复任务或无限累加备注 | 更新最新导入快照，保留旧值与运行记录，验证重复导入为零变更 | 悄悄恢复历史累加；无依据抹掉手写备注；在写入结果不确定时盲目重试 |
| P08 | 结果必须真实且可追溯 | 分别标记计划、已验证写入、未执行、失败、不确定、源排除 | 用绿色成功状态掩盖部分失败；将 39 个未处理项目隐去；只报测试数量而不报证据范围 |
| P09 | 业务测试的预期也属于保护对象 | 根据明确批准的业务变化更新预期，并保留批准依据 | 为了让测试通过而删除反例、放宽身份断言、排除失败测试且不披露 |
| P10 | 本契约不能由执行者自行解除 | 用户明确批准后做限定范围、可追溯的版本修订 | 在同一修复任务中自行改规则、改检查，再宣称原规则仍获满足 |

公开版不包含生产 Base、表、字段或记录 ID。真实绑定在受控本地配置中维护，执行前读取实际结构核对。关键对象包括 Tasks 完成勾选框、Tasks → Projects 链接和 Projects → Factories 链接。

字段改名与字段删除后重建是两种不同操作，不能只根据用户看到的名称判断安全性。

## 4. 当前实现，不得冒充永久确认的业务规则

下列规则当前存在，后续可提出改进，但不得借“修 bug”悄悄改变。涉及变更时先做专项说明：

- 项目编号 + SKU + 工厂共同核对身份；目前不自动新建缺失 Project。
- 已批准的工厂别名清单；未知别名不等于不存在工厂。
- First CRD 缺失时采用 MP 减 45 个自然日估算；估算值必须标明来源。
- Next PLM 生成普通任务；不是所有任务都是 Master Milestone。
- 来源日期删除线/多日期/缺少年份的处理、里程碑对应关系、任务负责人推导。

这一区域不是对上述业务规则进行新的用户确认。是否适合未来需求须单独核对，不能以“已经写进代码”为依据拒绝修正错误。

## 5. 每次合作的强制流程

### 开始前：先查保护规则与影响

读取本契约和相关调用链；用简短中文交代：本次做什么、触及哪些保护项、哪些输入变化会影响功能、哪些条件尚未验证。例行修复无需反复审批，但解除保护必须专项批准。

### 执行中：基线先于修改

保留可恢复的源码基线和脱敏结构证据；标明实际数据采集时间。先复现问题，再修改，再验证。新发现阻断要及时说明，不能等交付时才第一次解释。

对受影响对象停止不确定写入；只有在能够证明其余对象不依赖该问题时，才继续处理其余已授权对象。

### 交付前：明确证据边界

交付必须包含以下六项，可以很短，不能省略：

1. 改了什么，版本和启动入口是什么。
2. 现在能够处理什么。
3. 不能处理什么；具体项目/数量/原因/下一步是什么。
4. 用户可以正常改什么，哪些变动需要程序重新核对。
5. 验证到哪一层：代码测试、真实来源重放、模拟写入、真实线上写入、线上读回验证分别说明。
6. 如何恢复，恢复有哪些条件；未保留恢复基线时不能承诺“一键回滚”。

“完成”只能覆盖已经验证的任务范围。存在关键链路未通过时，明确写“未完成/待核实”，不得用“可用”代替边界说明。

## 6. 如何解除某一项保护

执行者先提供具体变更单，包含：规则 ID、改前、改后、业务理由、受影响对象、数据迁移预览、验证结果、恢复办法。用户对这些具体内容的明确同意才构成批准；不要求使用某句固定口令。

批准仅覆盖该变更单，不扩展到其他规则。先修订有版本的契约和预期，再执行已批准变更，最后验证与留档。不得事后补写批准。

## 7. 真正的技术硬保护需要什么

仅有 AGENTS.md、文件只读属性或执行者能同时修改的测试，不能证明“绝对改不了”。要实现未经批准无法进入正式版本，应进一步落实：

1. 独立受控的代码仓库：正式分支保护、禁止强推、执行者不能绕过审核；保护契约和测试要求用户或独立维护者审核。
2. 必须通过的检查：结构漂移、checkbox 完成语义、身份冲突、重复导入、部分失败呈现、源文件变更与读回验证。测试/门禁规则本身也受保护。
3. 正式运行只使用已审核的版本；能直接改本地源码并运行时，本地文件仍可绕过仓库门禁。
4. Airtable 端使用实际可用的最小权限，限制结构修改、删除与无关表访问；能力不足时明确剩余风险，不能声称已禁用某权限。
5. 应用在执行前读取真实结构与目标数据；发现不兼容就拦截受影响写入，并显示具体差异。外部管理员对 Airtable 的修改无法由本地文档阻止。

**以上是后续技术落实清单，不是已部署状态。** 设置前必须检查仓库、账号权限、审核人和实际部署方式；不得在没有证据时打“已保护”标记。

- 原始 `(2).xlsx` 未在本次可用位置找到，使用了运行日志重放；其他版本的 workbook 验证不能替代该文件。
- 本次规则只在当前源码项目落地；旧 EXE、其他工作区、未加载规则的 AI 和用户手动云端修改不受本文技术控制。

后续发现的新限制必须追加在对应交付记录中，并更新本节；不得删除未解决限制以简化说明。若更新涉及保护规则本身，遵循第 6 节。
