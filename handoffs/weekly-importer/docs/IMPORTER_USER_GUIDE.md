# 周报导入工具：使用说明与修改限制

文档版本：1.0 · 2026-09-23。适用实现：本机 AutoPM **2.5.0-rc5**。示例项目和型号均为虚构。

> 本说明发布不等于发布了 rc5 程序。GitHub 历史交接源码可能仍是 2.4.0-rc6；请看程序窗口标题和源码 `autopm/__init__.py`。旧 EXE 不会因为文档更新而升级。其他版本必须重新核对行为。

## 先记住这六条

1. **正文、明确的业务日期可以正常更新；标题、表格结构和身份值不能当作普通正文随意改。**
2. 周报只读取唯一、可见的 `Report` 工作表。其他页上的信息不会自动导入。
3. 项目编号、SKU、工厂必须与 Airtable 中的目标对应；有项目不代表所有任务已导入。
4. 日期单元格的绿色填充和删除线有业务含义，不能随意用于装饰。
5. 先看预览，确认后才写入；“Ready to write”不是已经写入。
6. 改了文件、设置或结构后重新分析和预览；结果不确定时先核对，不连续重复点写入。

## 1. 工具做什么，不做什么

| 工作 | 当前范围与边界 |
|---|---|
| Weekly Report → Airtable | 从支持的项目区块提取项目字段、时间线任务和问题；核对目标后预览并写入 |
| Airtable → All Tracker | 可独立读取，不必先导入周报；导出更新后的 Excel 副本 |
| All Tracker → Airtable | 基于本工具生成的导出基线，有限回写经预览的改动；普通任意 Excel 不具备这个基线 |
| 缺少 Project | 当前严格身份模式不会凭周报自动建立缺失 Project。先建立或修正项目主数据 |
| 缺少 Task | 目标 Project 能唯一匹配、任务来源和字段映射有效时，可生成新增 Task 计划 |
| 删除/合并 | 周报少一项、空一格、去掉绿色，都不是自动删除或合并云端记录的命令 |
| 闭环保证 | 读回验证确认本次字段写入；不能保证其他 Airtable 自动化之后不会再修改，也不是全库事务 |

## 2. 周报修改红绿灯——你到底能改什么

“可以改”指可正常维护真实业务内容，不代表新内容一定与 Airtable 的身份、选项和人员一致。每次导入仍要看预览。

| 周报对象 | 分类 | 你可以怎么改 | 必须避免 / 改后怎么检查 |
|---|---|---|---|
| 文件名、存放目录 | 可以改 | 改名、另存副本后重新选择 | 文件名不是项目身份；不要在预览后替换原文件 |
| Engineering update / Current Progress 正文 | 可以改 | 更新本周实际进展，保留原标题和所在格 | 不要粘贴整段历史导入快照或 `--- YYYY-MM-DD ---` 分隔行；空白不是清空指令 |
| 问题、行动描述 | 可以改，但检查结果 | 修改事实与行动 | 当前规则模式可能把改名后的问题识别为新问题；检查 Create/Update，不能承诺智能合并 |
| 里程碑日期 | 可以改 | 使用一个明确的 Excel 日期或 `2026-10-15` | `10/11` 在自动模式下可能有歧义；有多个有效日期不自动选最后一个 |
| 项目 Update / Report Date | 可以改 | 写实际报告日期 | 不要伪造新日期绕过旧报告检查；日期冲突不会被补充日期强行覆盖 |
| 姓名、负责人 | 可以改，但检查匹配 | 使用 Airtable 中能唯一对应的姓名 | 缩写、同名、未建人员可能无法匹配；不要把“未写负责人”看成全部任务失败 |
| 项目编号 | 需要身份核对 | 真实编号有误时可纠正 | 不能改成另一个项目来绕过报错；核对 Airtable，不能重复复制同编号区块充当新项目 |
| SKU 内容 | 需要身份核对 | 写完整真实型号，用逗号/换行分隔 | 不随意去型号后缀、空格、数字或国家标识；`AA100/200/300` 不会自动展开为完整型号 |
| 工厂名称或代码 | 需要兼容核对 | 使用标准名称或已确认的别名；工厂代码可改为 FAC | 新别名需要核对；真实换厂不是别名变更。不能合并同名但不同记录的工厂 |
| 项目名称、状态、类型 | 可以改，但检查选项 | 更新真实内容 | 状态等单选值须可映射到云端已有选项；不能假定会自动新增选项 |
| `Report` 工作表名称 | 不要随意改 | 保持 `Report`，大小写和空白有规范化支持 | 改成 `Weekly Report`、新增两个规范化后同名的页，可能无法解析 |
| Project Number、SKUs、Fty. 等标签 | 不要随意改 | 保留已验证模板标签 | 新标题、中文翻译、缩写和错别字不保证识别；改模板后先做解析验收 |
| 时间线任务标题 | 不要随意改 | 更新日期，保留已批准标题 | 任意改任务名可能匹配不上原任务或新增另一条；不能仅凭颜色推断同一任务 |
| 合并单元格、行列和标题层级 | 不要随意改 | 使用已验证模板复制完整区块 | 拆分/合并标题、单独移动日期、跨项目合并，可能改变提取归属；整块移动也要检查项目数和源位置 |
| 日期格绿色背景 | 具有业务含义 | 只为确实完成的任务使用明确绿色实心填充 | 不是装饰色；字体绿色、条件格式绿色不等于完成证据；其他颜色不表示重新打开 |
| 日期删除线 | 具有业务含义 | 明确划掉旧日期，并留下唯一有效的新日期 | 整格划掉则不导入；部分日期字符被划掉仍不明确。不能指望程序猜最新日期 |
| 公式和错误单元格 | 不作为可靠导入来源 | 导入副本中保留确认后的显式值 | 不直接依赖公式缓存；`#N/A` 等错误不当作业务值导入 |
| 隐藏行/列、隐藏 Report 页 | 不可用作排除开关 | 导入前在副本中取消隐藏并检查全部区块 | 隐藏行列仍可能被读取，不能用隐藏来表示“不导入”；隐藏 Report 主表会阻断。合并区域被覆盖的旧值另有排除逻辑 |
| 图片、批注、文本框、附件 | 不作为本链路字段来源 | 作为阅读辅助 | 不保证识别成字段、日期或任务；本工具不是截图 OCR 导入器 |
| 字体大小、普通边框、行高、列宽 | 通常可改 | 保持内容可读且结构不变 | 日期颜色、删除线、隐藏状态例外；大面积格式化空白区也可能触发大小限制 |

**未知格式先在副本预览。** 对新模板的安全性，必须由维护者拿实际文件验证，不能让使用者猜。

## 3. 文件与容量限制

- 支持 `.xlsx`、`.xlsm` 读取；旧 `.xls` 需先另存为 `.xlsx`。读取不执行宏，也不承诺导出保留宏。
- 唯一且可见的 `Report` 页，使用已支持的 Project Number 区块布局；不同布局需适配验证。
- 文件上限 40 MiB，解压内容上限 200 MiB；工作表行数 × 列数不得超过 1,500,000。
- 源单元格证据上限 80,000、总文本上限 2,000,000 字符、单格上限 32,767 字符；超限拒绝，不静默截断。
- 导入期间关闭对同一文件的编辑。推荐保存独立输入副本，避免预览时内容与写入时内容不同。

## 4. 字段去哪了

以下是当前主库配置语义，不代表任何同名新建字段都可以自动接管。其他 Base 必须重新核对。

| 周报内容 | 目标 / 行为 |
|---|---|
| Current Progress / Engineering Remarks | Projects 的 Engineering remark(Manual)：最新导入快照，历史原值在预览和日志保留 |
| Eng Update This Week | Projects 的 Current stage 多行文本字段；不要误映射到另一个相近名字的单选字段 |
| 明确时间线任务 | Tasks：名称、项目关联、Due Date；适配已有里程碑选项 |
| 时间线日期绿色填充 | Task Done (Manual) = True；不修改公式状态、不推断 Completed By、不自动取消完成 |
| Task Start Date | 不把报告日期自动当成所有任务的开始日期；既有开始日期与其他排期流程需独立核对 |
| First CRD | 优先使用明确来源；符合既有规则时按 MP 减 45 个自然日估算，预览必须标明估算 |
| Next PLM | 项目 Next Action，并可产生名为 Next PLM 的普通任务；不是所有新增任务都属于主里程碑 |
| Issue 描述 / Action / Risk / Owner / Due | 分别进入 Issues 的受支持字段；创建时间由 Airtable 生成，不写 createdTime |
| Capacity 等未映射可选值 | 保留来源与提示，可能不写入；不应把该提示误称为整项目无法写入 |
| LOA、Jira 汇总、Jira URL | 需要符合已支持标题、数据类型与实际映射；叙述里出现一个数或超链接标签不等于有可导入字段 |

手写备注应与自动快照区域分开。不要把自由手写内容追加在 `--- 日期 ---` 自动快照内部，再假定未来导入永远保留它；该区域按最新导入快照处理。

当前 Project 编号 + SKU + 工厂校验是实现边界，不是永久业务决定。只有业务方案明确批准后，才能改变身份匹配规则。

## 5. 标准导入步骤

1. **检查版本**：标题 rc5；如果仍是旧窗口，先保存连接设置，关闭并用源码启动入口重新打开。
2. **保存输入副本**：更新完内容再保存，检查 Report 页、项目编号、SKU、工厂及日期格式。
3. **选择并分析**：核对解析项目数及每个重点项目的任务。规则解析和 AI 解析不是相同证据层；使用 AI 解析会将选取的报告内容发送到已配置模型服务，须符合组织数据使用规定。
4. **Preview in Airtable**：连接正确 Base，核对结构、项目身份及字段旧值/新值。搜索只是查看过滤器，**不是选择本次写入项目范围**。
5. **检查未导入项**：区分身份阻断、日期排除、缺映射、普通提示。一个项目 Ready 仍可能有部分字段被排除。
6. **Confirm Airtable Write**：确认的是该次完整有效计划；确认窗口和计划数量要一致。文件/设置变化、忙碌、阻断或过期预览需要先处理。
7. **检查实际结果**：只有写后读回确认才算 Written。保存 Run Logs，核对失败、不确定和未执行部分。
8. **更新 All Tracker**：可按需独立操作。回写使用本工具导出的 Excel 副本及配套 `.autopm.json` 基线，二者一起保存、不要手改基线。

## 6. 怎样读结果

| 显示 | 实际含义 | 下一步 |
|---|---|---|
| Preview only / Planned / Ready to write | 计划存在，尚未写入 | 审核后确认 |
| Written | 本次记录写入已读回验证 | 再看该项目是否还有排除项 |
| No changes / Already current | 已比较的受支持范围无需再写 | 不代表所有来源字段和任务都完整覆盖，仍须看排除提示 |
| Skipped / Needs action | 部分来源或项目未进入写入计划 | 按具体原因修正，重新预览 |
| Blocked | 存在阻断当前执行的条件 | 先修复结构、配置或计划问题 |
| Partial / Check write | 已有部分写入，或结果尚不确定 | 先核对云端和日志，再生成新预览；不要盲目重试 |

顶部项目数按项目分组，不等于记录变更数。一个项目可能同时更改 Project、多个 Task 和 Issue；任务变更数也不等于来源时间线任务数。

## 7. 常见故障与处理

| 现象 / 原因 | 你该做什么 | 维护者应验证什么 |
|---|---|---|
| 工厂未知或重名 | 对照标准名称；真实换厂先核实项目关联 | 工厂候选与别名、项目/SKU 上下文，不任意删代码后缀 |
| Project 存在但任务未导入 | 查看身份阻断和来源任务数 | 追到源单元格 → 解析结果 → Project 记录 → 任务计划，不能仅看截图 |
| SKU 不重叠 | 核对完整型号，不自行删字母/数字来凑匹配 | 展示双方型号，区分打字错误、产品变型和真实业务变更 |
| 找不到 Project | 检查正式编号、SKU、工厂及建档情况 | 明确“缺项目”与“缺任务”是不同问题 |
| 日期未导入 | 在来源填唯一明确日期，检查删除线与年份 | 源日期是否有效；避免选错旧日期、公式缓存或其他项目日期 |
| 完成标记没同步 | 检查日期格明确绿色填充、checkbox 映射 | True 的源证据、真实字段类型；不能写公式结果 |
| 确认按钮没有继续 | 查看忙碌/过期/无变更/阻断提示 | 若完全无反馈，属于缺陷，检查 UI 错误日志，不让用户无限重复点击 |
| Record Date read-only 报错 | 使用已修复版本并重新核对映射 | createdTime 可读不可写，不能因此跳过全表 |
| 备注不断累加 | 核对版本、是否粘贴了历史快照 | 重复预览应为零新增变更，旧值应留日志 |
| 网络超时 / 422 / 无权限 | 保存错误信息与运行编号 | 只读重试与写入不确定分开；不泄露 Token，不放宽字段校验 |

## 8. 其他地方也有修改边界

### Airtable

- 业务值可按职责维护，但改变项目/SKU/工厂关联会影响身份；正在导入时避免同时修改目标记录。
- 字段改名先核对消费者。稳定 ID 能帮助本工具适配改名，但其他公式、脚本、自动化仍可能依赖名字。
- 删除重建字段、改变类型、把链接改到另一张表、合并记录，属于结构或身份变更，需正式变更方案。
- 字段说明是提醒，不是权限锁；已存在描述也不代表规则全部生效。

### All Tracker

- 修改导出副本前保留基线；支持范围以本次回写预览为准。
- 项目编号、SKU、工厂、来源绑定不能随意改；删除列或清空单元格不意味着删除云端值。
- 当前往返链路保护 P/Q/R 列，不应假定这些列可通过本工具回写；不要插列移动受保护布局后继续使用旧基线。
- 更换模板、排序/拆分/合并造成身份不唯一时，需要重新验证；不以“文件能打开”作为回写验收。

### 设置、映射与程序

- 换 Base、Token、字段映射、日期策略或程序版本后，重新生成预览。
- 映射记忆里的字段被删后，不自动转投同名字段。新 Base 不能直接沿用旧 Base 的标识。
- 不手改旧预览、写入日志或导出基线来绕过错误；保留它们作为排查证据。

## 9. 已知验证边界

- rc5 对当时真实记录完成 526 条本地模拟变更及重复预览 0 变更；126 项核心测试通过。模拟不证明生产权限、限流及云端自动化已经通过真实验收。
- 当时仍有 39 个项目存在身份/来源冲突；这是历史审计状态，不是以后每次运行的固定数量。业务明细仅保留本地，不在公开说明中发布。
- 原始受测周报某一版本不可得，使用保存的解析日志重放；另一个版本的原文件解析不能冒充相同来源验证。
- 完整历史测试库并非全部通过；核心链路通过不能替代所有旧界面、旧语义和所有未来模板的验收。
- AI 模型、规则解析器、颜色识别都不保证所有新布局自动兼容。新增模板或变更关键格式必须补真实样本回归。
- 导入不是全库事务；并发写入与后续自动化仍有风险，须按结果逐项核实。

## 10. 出错时提供什么

提供版本、运行编号、源文件版本、一个项目的源位置、预期与实际结果、具体错误和脱敏日志。不要在公开 GitHub 上传真实周报、完整记录快照、人员信息或凭证。

维护者必须：复现 → 定位共享原因 → 修复 → 增加最小回归检查 → 用真实资料重放 → 对照重复导入 → 更新限制和版本 → 说明发布/线上验收状态。用户不承担猜测软件隐藏规则的责任。
