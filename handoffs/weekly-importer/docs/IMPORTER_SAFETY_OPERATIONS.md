# 双层保护与变更操作规程

版本 1.0 · 2026-09-23。适用范围和版本边界见 [使用说明](IMPORTER_USER_GUIDE.md)。

## 两层分别保护什么

| 层 | 做法 | 能解决什么 | 不能保证什么 |
|---|---|---|---|
| GitHub 规则与版本 | 契约、用户说明、变更记录、单独分支与 PR、规则编号 | 避免规则只存在聊天里；可以追溯版本和改动范围 | 文档不是强制审核；无分支保护时有写权限的人仍能绕过 |
| Airtable 操作现场提醒 | 关键字段保留旧描述，追加带版本的导入注意事项及说明链接 | 用户改字段或关联前能看见用途、风险与下一步 | 备注不阻止手改，也不能锁住 Excel 模板 |

第三个入口是周报使用说明：它明确列出颜色、删除线、标签、日期和布局限制。可把这份说明链接放在模板的独立 `Instructions` 页，不能在 `Report` 页项目区块之间插入说明行。本次尚未修改用户的原始模板。

## 当前保护状态

- 已建立：本地协作契约及 AGENTS 入口；本次发布说明、版本与限制。
- GitHub 只读检查：仓库为公开；检查时 rulesets 列表为空，main 未保护。本次不改变仓库权限或审核人。
- Airtable：20 个关键字段已追加说明并逐项读回验证，原描述保留，字段名称/类型未变；不能由此推断权限锁已经配置。
- 未建立：独立审批账号、执行者不能绕过的分支保护、发布强制门禁、Airtable 结构编辑角色隔离。
- 当前 GitHub 执行账号拥有管理员权限，因此执行者与保护管理员尚未分离，不能声称“绝对不能改”。

## 真正的硬保护实施方案

1. 用户保留保护规则管理权，日常执行身份使用不能修改仓库规则的账号或应用。
2. 正式分支要求 PR、独立审批、必要检查通过；新提交使旧审批失效，禁止强推/删除，并核对管理员与绕过权限。
3. 保护契约、CODEOWNERS、工作流、测试预期和生产写入逻辑共同纳入审核，不能只保护代码文件。
4. 日常操作角色只获得所需数据编辑权限；结构编辑由指定维护者负责。字段权限和 API 身份要一起核对，不能配置后反而把合法导入全部阻断。
5. 正式运行使用已审核版本，登记版本和源码哈希；本地自由修改源码的运行不受远程分支门禁约束。
6. 在测试环境验证阻断真实生效，再记录上线与恢复条件；不能只截图显示“Enabled”。

以上方案没有在本次自动启用：涉及账号职责和权限变化，须先明确独立审核人与允许的写入角色，再提出具体设置。尤其不能让同一个管理员账号创建 PR 后自行充当独立审批人。

依据：[GitHub 分支保护](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)、[Airtable 字段/表编辑权限](https://support.airtable.com/articles/2296468758)、[Airtable Base 角色](https://support.airtable.com/articles/5450095623-airtable-base-permissions)。功能和套餐应以执行时真实环境核对为准。

## 每次改动都使用同一张变更单

| 必填项 | 内容 |
|---|---|
| 变更编号 / 保护规则编号 | 唯一编号；涉及契约 P01–P10 的哪几项 |
| 修改对象 | 文件、模板标题/区域或表字段；真实内部 ID 只放受控记录 |
| 改前 → 改后 | 具体业务行为，不能只写“优化” |
| 影响范围 | 周报解析、匹配、写入、读回、Tracker、自动化和界面 |
| 批准 | 用户对具体规则变化的明确授权；普通兼容修复沿用已有授权 |
| 验证与限制 | 通过、失败、未验证分别列出；附复现和真实数据重放边界 |
| 恢复 | 源码基线、字段原描述、原值日志；并发修改后不得盲目恢复旧值 |
| 发布 | 提交、PR、是否合并、用户实际运行版本；发布文档不等于发布程序 |

## 防止回归的必查用例

- 工厂代码改成 FAC 后，同一个真实工厂仍能正确匹配；陌生别名或不同工厂不能误合并。
- 项目存在但任务为空时，可产生有源证据的新任务；身份失败必须显示“未比较”，不是“无变化”。
- checkbox True 与公式字段读写边界正确，不凭非绿色清除完成状态。
- 唯一有效日期与整格删除线、部分删除线、多日期、公式缓存正确区分。
- 重复导入没有重复记录和备注增长；老报告不能覆盖更新内容。
- 文件/配置/结构变化使预览失效，执行前核对，写后读回；部分失败保持真实状态。
- 新模板需真实样本；测试失败不得以删除保护断言处理。语义确有批准变化时记录依据再改测试。

## Airtable 备注维护方法

使用独立标记段 `AUTOPM IMPORT GUIDE v1.0`，保留原描述，追加“用途、允许改动、需核对的变动、说明链接”。不改字段名称、类型、公式、选项或业务记录。

写前保存原描述及 ID，写后重新读取并检查全文；记录成功、失败和 action ID。未来更新只替换本工具的标记段，不覆盖其他维护者描述。恢复前先比对当前描述是否仍为本次写入版本，否则需人工合并。

## 交付固定格式

每次交付都说清：改了什么 / 能做什么 / 不能做什么 / 用户能改什么 / 验证到了哪层 / 剩余问题 / 版本入口 / 恢复边界。存在未处理项目时，不能以“全部可用”收尾。
